# Public launch readiness

Tape's public product is a virtual-trading terminal backed by a Spring Boot monolith and PostgreSQL. Users do not need a brokerage or Demat account. The existing order engines use server-side synthetic prices and keep the provider adapter outside the execution path.

## Multi-user foundation

- Registration and initial funding run in a database transaction. Each user gets independent ₹10,00,000 virtual wallets. The permitted-market-data account remains disabled for trading. Authentication binds requests to a server-side principal. Wallet, order, position, and watchlist queries scope ownership using that principal. PostgreSQL constraints and account locks protect reservations, immutable postings, and per-account idempotency on writes.
- Apply Flyway V12 and reapply the account runtime grants before starting HTTPS replicas. Spring Session shares session rotation and logout across replicas using PostgreSQL. Authentication admission includes persistent, atomic address, normalized-identity, and global budgets. Email verification and recovery require a configured delivery channel and provide session revocation. See [identity readiness](identity-readiness.md).
- The equity matcher, options and futures scheduling, and reconciliation each use a distinct PostgreSQL advisory transaction lock. The connection holding the lock never owns the trading transactions. This prevents concurrent scans while the lease holds. Per-account locks, state transitions and immutable event keys still decide correctness if a node crashes, a lock connection disappears, or a subsequent scan repeats work. Cursors may restart from the beginning. Budget one extra database connection per simultaneously active worker on a node for these locks and set database idle-in-transaction timeouts with the maximum expected scan time in mind.
- The protected operations endpoints provide liveness, PostgreSQL readiness and metrics. Readiness checks V11 tables and their runtime grants as well as database connectivity. Watch `tape.worker.runs`, `tape.request.admission`, `tape.auth.admission`, `tape.market.admission`, `tape.market.stream.polls`, and the existing execution, quote-age and reconciliation counters. Worker errors log the worker name and exception class. The existing reconciliation logs use hashed account references. Keep operations endpoints private.

### Licensing path

1. Ask the prospective provider and the relevant exchange licensing teams for a written grant covering exchange segments, public audience, user entitlement model, education eligibility, delay, storage and retention, charts, exports, replay, derived P&L, and simulated fills as separate purposes.
2. Obtain a review of the actual product and data flows against the cited circulars and agreements before choosing a real-data launch. Start with permission for reference data and embargoed display. Add replay as a separate scope if explicitly granted.
3. For an approved multi-user arrangement, store service credentials in the server's secret manager and map user/tenant permission to the written grant. Partition provider connections and caches by credential and entitlement scope. Union subscriptions only within a sharing scope that allows it. Keep per-user and provider budgets, audit entitlement decisions and disconnect or expire access on revocation. Return an unavailable status during an outage and use explicit source timestamps. For any later approved replay, enforce the source embargo both before ingestion and before read or computation. Keep fills isolated until their own approval and replay-engine tests pass.

## Technical checklist

1. **Before public registration.** Verify the configured email sender's deliverability and abuse controls. V12 provides verified email, expiring random single-use hashed tokens, generic public responses, throttling and revocation of prior sessions after password reset. Review service secrets, TLS, forwarding-header trust, database network isolation and data retention.
2. **Before multi-instance rollout.** Validate shared-session behavior behind the actual HTTPS edge. Test rate limits and cuts across replicas, set connection-pool budgets, run load tests on signup and workers, and verify readiness, graceful draining, backups, and a restore/reconciliation drill. Apply Flyway with the migration role, keep credentials separate at runtime and ensure rollback accounts for the shared-session cutover.
3. **Before enabling a licensed provider.** Implement grant provisioning, entitlement-aware quotas and cache boundaries, a durable data-access audit trail, and a replica strategy for the feed gateway. The current local subscription registry and provider limits are intentionally process-local. Validate the exact rights and production contracts with genuine calls only inside the approved scope.
